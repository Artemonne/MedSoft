# Демонстрация лабораторной работы №4

## До показа

Нужны Node.js 20.19+, npm, PostgreSQL, OpenSSL и приложение-аутентификатор для TOTP. Команды
выполняются из корня репозитория. Если стенд ещё не подготовлен:

```powershell
npm install
Copy-Item backend\.env.example backend\.env
npm exec --workspace backend -- prisma migrate deploy
npm run certs:generate
npm run jwt:generate
npm run admin-bootstrap:generate
npm run certs:verify
```

Перед миграцией задайте корректный `DATABASE_URL` в `backend/.env`. Для первого запуска завершите
на `https://localhost:5173/admin/setup` bootstrap администратора и TOTP по одноразовому секрету.
Для браузера импортируйте публичный `certificates/local/ca.cert.pem` в доверенные корневые
сертификаты текущего пользователя. Не показывайте на записи экрана API-ключ, bootstrap secret,
TOTP seed, JWT или содержимое приватного ключа.

XML преподавателя отсутствует. Для этой демонстрации используется исключительно синтетический
`docs/lab4/demo-patients.xml`; это не заявление о совместимости с неизвестным форматом.

## Сценарий защиты

1. Запустите HIS:

   ```powershell
   npm run dev
   ```

   Откройте `https://localhost:5173/admin/login`, войдите паролем администратора и текущим
   шестизначным TOTP-кодом. Backend одновременно слушает HTTPS API на `localhost:3001` и
   MLLP/mTLS на `127.0.0.1:2575`.

2. Откройте «Сервисные аккаунты», нажмите «Создать сервисный аккаунт», задайте имя, например
   `Patient Import`, выберите роль `HL7 Import` и создайте аккаунт.

3. Скопируйте показанный один раз API-ключ в безопасное временное место. Не закрывайте диалог до
   копирования. В БД полный ключ не хранится.

4. В отдельном PowerShell выпустите клиентский сертификат с тем же именем аккаунта в CN:

   ```powershell
   npm run certs:generate-client -- -ServiceAccountName "Patient Import"
   npm run certs:verify
   ```

   Сохраните показанный путь к каталогу
   `certificates/local/clients/<name>-<hash>/`. Потребуются `client.cert.pem`, `client.key.pem` и
   `certificates/local/ca.cert.pem`. CN носит справочный характер; авторизация выполняется JWT.

5. Запустите настоящее Electron-приложение:

   ```powershell
   npm run dev:hl7-importer
   ```

   Альтернатива после `npm run package:hl7-importer` —
   `hl7-importer/release/win-unpacked/MedSoft HL7 Importer.exe`.

6. В разделе настроек укажите:

   - Base URL: `https://localhost:3001`;
   - MLLP host: `127.0.0.1`, port: `2575`;
   - TLS server name: `localhost`;
   - Source System ID: `DESKTOP-IMPORT`;
   - API-ключ из шага 3;
   - клиентский certificate/key из шага 4;
   - CA: полный путь к `certificates/local/ca.cert.pem`;
   - timeout: `10000` мс.

7. Нажмите «Проверить соединение». Покажите отдельные успешные результаты: получение JWT и
   `GET /api/testConnection` по HTTPS, затем TLS 1.3 mTLS handshake, тестовый QBP Q11 и корректный
   ACK по MLLP. Отключения TLS-проверки в приложении нет.

8. В результате проверки покажите Subject/Common Name, Issuer, срок действия, serial number и
   SHA-256 fingerprint серверного сертификата, а также успешную проверку цепочки и имени
   `localhost`.

9. Перейдите к импорту, выберите системным диалогом
   `docs/lab4/demo-patients.xml`. Покажите число найденных пациентов, внешний ID, ФИО и начальный
   статус каждой строки.

10. Запустите импорт. Покажите, что строки последовательно переходят через статус отправки и что
    каждому пациенту соответствует отдельный ADT A28 и отдельный ACK. Медицинские данные не
    уходят во внешние сервисы.

11. После завершения покажите счётчики и внутренний числовой ID HIS в каждой успешной строке.
    Этот ID получен из `MSA-3`, а не сгенерирован desktop-клиентом.

12. Войдите в HIS как медработник с правом просмотра пациентов и откройте «Пациенты». Найдите
    синтетические записи и откройте карточку по внутреннему ID. Административный интерфейс не
    предоставляет список пациентов, поэтому этот шаг выполняется именно в рабочем интерфейсе
    `/app/patients`.

13. В карточке/медкарте покажите связанные диагнозы; при необходимости справочник диагнозов
    доступен соответствующей роли. Импорт создаёт отсутствующий диагноз по шестизначному коду и
    переиспользует существующий.

14. В desktop повторно выберите тот же XML и запустите импорт. Покажите индивидуальные ошибки
    дубликата. В HIS убедитесь, что число пациентов и исходные данные не изменились; диагнозы из
    отклонённого сообщения также не создаются.

15. Снова войдите администратором, откройте «Аудит» и найдите события
    `HL7_PATIENT_IMPORTED`/`HL7_PATIENT_IMPORT_FAILED`. Покажите subject, issuer, serial number,
    SHA-256 fingerprint и период действия клиентского сертификата. JWT, API-ключ и медицинские
    поля в аудите отсутствуют.

16. Продемонстрируйте минимальные права роли. С access JWT этого сервисного аккаунта
    `GET /api/testConnection` успешен, а обычная защищённая операция, например
    `GET /api/patients`, получает `403`. В интерфейсе desktop это ограничение не обходится; для
    технического показа запроса можно использовать инструменты разработчика/API-клиент, не
    выводя сам JWT на экран или в сохраняемый лог.

## Ожидаемый итог

У каждого пациента есть отдельный результат и HIS ID, в БД нет повторов пары Source System ID +
внешний ID, диагнозы и аудит сохранены атомарно. Повторный импорт отклонён без изменений. Если
проверка XML преподавателя обязательна, демонстрация этого пункта остаётся заблокированной до
получения реального файла/XSD и проверки изолированного адаптера.
